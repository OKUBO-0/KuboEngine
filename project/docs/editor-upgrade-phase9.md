# KuboEngine Phase 9 専門機能の採択

Phase 1〜8で整えた編集・実行・配布の流れを使い、次の実装を **地形制作** と **Foot IKの接地検証** に決めた。前者は「光の回廊」の屋外区間を制作するため、後者は既存の歩行モデルで段差を越える際の足の滑りと浮きを減らすために使う。対象シーンと数値は今後の実装・比較に使う初期の合格条件として設定した。

## 比較に使った資料と計測

- 添付フォルダーは `dx12-engine-v1.10.0`。同梱の `version.txt` は **2.6.1** で、初期ロードマップの比較記録にある2.5.6とは版が異なる。今回の採択では、添付のLua定義、シェーダー、サンプルを確認した。各専門機能のUnoEngine上での実行速度や画質は測定していない。
- 「光の回廊」はHubの3Dテンプレートから作成した。Editorでタイトルを編集して保存し、PlayからPrefab、Trigger、結果画面、Stopへ進んだ。欠損した共有マテリアルによるExport拒否を確認し、復元してDebug・Releaseの配布版Playerで結果画面まで実行した。標準Playerの配布検証は試験用の自動進行を利用し、別のPlayer実行テストは入力フレームにマウスとA／Wを与えて、壁との衝突、ゴール時のHUD更新とパーティクルを確認した。
- Phase 7の同一シーン・320×320・各24フレームの計測では、昼のCPU記録時間は0.194 ms、GPU描画は0.047 ms、夜はそれぞれ0.233 msと0.074 ms。全102,400ピクセルで昼夜の差が出て、夜の再読込後の画面は一致した。この計測の対象はマテリアルと環境の比較で、広域地形や多数のインスタンスの性能は次の検証で測る。

配布検証と入力操作の再現に、次のスクリプトとテストを使う。[配布検証](../tests/phase8_corridor_checks.ps1) · [シーン生成](../tests/prepare_phase8_corridor.ps1) · [Playerテスト](../tests/player_runtime_checks.cpp)

## 優先順位と判断

| 順位 | 候補 | 添付資料で確認した範囲 | KuboEngineでの判断 |
|---:|---|---|---|
| 1 | 地形制作 | 初期比較で地形とスカルプトが候補に挙がった。今回の添付では水面と植生の描画用シェーダーも確認した | 採択。「光の回廊」の屋外区間に、主要ルートと斜面をSceneで調整できる地形を作る |
| 2 | Foot IK | `tools/lua-defs/dx12e.lua` にFoot IKの重み設定と取得があり、Play中の接地補正と記載がある | 採択。既存の歩行モデルと箱コライダーでオン／オフを比較できる接地補正を作る。動的な足場や全身IKは後続候補 |
| 3 | 植生・水 | `shaders-src/foliage` にカリング、風、深度用コードがあり、`shaders-src/water` に水面と水中のコードがある | 地形の合格後に再判断。屋外区間の視認性や移動ルールに必要な効果から選ぶ |
| 4 | マテリアルグラフ | 添付の `shaders-src/templates` に複数の描画テンプレートがある。今回確認したファイルではグラフ編集の操作と保存形式までは確認できなかった | 共有マテリアルの色、粗さ、反射強度で現行作品の床と出口標識を制作できた。複数の作品で再利用する合成処理が出た段階で、必要なノードと保存形式を決める |
| 5 | 高度物理 | 初期比較で候補に挙がった。今回の作品はKuboEngineの箱コライダー、Trigger、固定更新で成立した | 今後の作品で動く足場、押し出し、段差乗り越えのいずれかが制作条件になった時点で、必要な形状と接触ルールを再評価する |
| 6 | 高度GI・仮想ジオメトリ | `shaders-src/screenspace/SSGI.hlsl`、`SSR.hlsl`、`shaders-src/vg` の可視性・クラスタ処理を確認した | 同条件でGPUのどのパスが律速かを測ってから選ぶ。320×320の環境比較から大規模ジオメトリの必要性は判断できない |
| 7 | Network | Lua定義にホスト／参加、NetworkIdentity、NetworkTransformに関する記載がある | 同期が制作条件になる作品が決まった段階で再評価。候補作品では2台の接続、切断復帰、状態再同期を検証する |
| 8 | 外部ハードウェア | `samples/GroveLab` にプロジェクトとArduinoファームウェアがある | 対象の機器と入力動作が決まった段階で検証する。現時点の作品はキーボードとボタンの操作で成立する |

## 地形制作に着手する条件

| 項目 | 内容 |
|---|---|
| 対象作品 | 「光の回廊」の屋外区間。屋内出口から、起伏を通って次のゴールを見つける区間を追加する |
| 作業開始地点 | Scene／Gameビュー、GUIDアセット、Undo／Redo、共有マテリアル、基本コライダー、RaycastとExportが使用可能。地形用の高さデータと衝突処理を設計するところから始める |
| 先に用意する基盤 | 32 m四方・1 m間隔の高さデータ、GUIDとバージョン付き保存形式、描画メッシュと物理のサンプリング規約、静的地形の広域判定 |
| 成果物 | 高さの上げ下げと平滑化ができるブラシ、1ストローク単位の履歴、地形アセット、Exporterの参照検査、地形の上を移動できる独立Player |
| 検証シーン | 開始地点、稜線、谷、斜面、ゴールを持つ「屋外回廊」。平地シーンとの比較に、同じカメラ、表示解像度、入力列を使う |
| 作業終了地点・合格条件 | 3種類のブラシ編集を各1回のUndoで復元し、Redoと再読込で高さデータが一致する。10点のRaycastと対応する描画面の高さの差が0.05 m以内。上り下りとゴール到達がEditorと配布Playerで再現し、コライダーの通り抜けは0件。1920×1080で300フレームを採り、同じGPU・同じ設定で描画時間と物理時間のp95を記録し、全体の60 fps予算16.67 msを合格目安にする |

## Foot IKの接地検証に着手する条件

| 項目 | 内容 |
|---|---|
| 対象作品 | 「既存ウォークモデルの接地検証シーン」。`Resources/models/walk/walk.gltf` の左右の脚・足・つま先のジョイントを使用する |
| 作業開始地点 | Controllerのクリップ、レイヤー、マスク、実行時遷移、スクラブ、固定更新、Raycastが使用可能。接地フェーズとモデルの骨マッピングを定義するところから始める |
| 先に用意する基盤 | 左右の股関節／膝／足のジョイントマッピング、歩行クリップ中の接地ウィンドウ、Raycastの法線、モデル空間とワールド空間の座標変換 |
| 成果物 | Foot IKの有効化と重みのInspector設定、Controller合成後の脚補正、現行のポーズへ戻る重み0の動作、EditorとPlayerで同じ入力を再生する比較記録 |
| 検証シーン | 平面、15°斜面、20 cmの段差。箱コライダーで構成できるため、地形制作の実装を待たずに検証できる |
| 作業終了地点・合格条件 | 左右それぞれの接地中の足裏と接触面の差を計測し、20歩中95%以上を0.05 m以内にする。重み0で元のポーズに戻り、ジョイントが欠けたデータは診断を出して元のポーズで動く。保存・再読込後に同じ重みと接地をEditorと配布Playerで再現し、固定入力でCPU・GPUの追加時間を記録する |
